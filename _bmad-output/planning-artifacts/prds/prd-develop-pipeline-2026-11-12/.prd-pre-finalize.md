# PRD: Agentflow MVP
*Working title — confirm.*

## 0. Document Purpose

This PRD is the build input for a personal tool. It is written so a code-generation workflow can turn it into epics, stories and code without re-deriving intent. Vocabulary is fixed in §3 Glossary and must be used verbatim. §4.0 lays out the pipeline as numbered sequential steps; features are grouped in §4.1–4.13 with globally numbered FRs (FR-1 … FR-N), each with testable consequences. Inferred items carry inline `[ASSUMPTION]` tags, indexed in §11.

Inputs it builds on: the v5 decision doc `agentic-workflow-mvp.md` (2026-11-11), the answered question bank `opportunity-questions.md`, and the decision log `.memlog.md` in this folder. Technical detail (tool list, file layout, YAML schemas, build order, AI-DLC/BMAD mapping) lives in `addendum.md`. Where this PRD and v5 disagree, this PRD wins.

## 1. Vision

Agentflow turns an assigned Jira story into a reviewed, tested pull request inside VS Code Copilot agent mode, with the developer acting only at a few deliberate decision points. It combines AI-DLC's lifecycle discipline (an explicit stage graph, gated approvals, one record per piece of work, deterministic checks that can block) with BMAD's lean working habits (a condensed spec, an append-only decision log, walkthrough-style review, recorded pitfalls).

Its defining constraint is **token economy through determinism**. Everything that can be computed (polling, ordering, scheduling, running tests and checks, building trace matrices, watching CI, moving Jira cards) is done by a TypeScript MCP server with zero model calls. Models are used only where judgment is unavoidable: writing the spec, planning, writing and refactoring code, and reviewing behaviour against requirements. Cheap models do most of that work; stronger models are used only when a human approves an escalation.

The developer starts the pipeline by moving a Ticket to In Execution in Jira, and approves at three fixed moments: after the Spec, after the Plan (or Patch Plan), and before the push. A fourth approval appears only when a cheap agent is stuck and asks to escalate to a stronger model. Approval comes through an MCP elicitation prompt that only a human can answer, so no agent can approve its own work.

## 2. Target User

### 2.1 Jobs To Be Done

- **Functional:** take a well-formed Jira story from Backlog to "In Tests" with a green CI run and a PR, without hand-writing the routine code and tests.
- **Functional:** spend premium Copilot requests only where a model adds value; never pay a model to run a command or read a log.
- **Control:** decide what gets built (spec, plan), when a more expensive model is worth it, and what leaves the machine (push).
- **Learning:** have every correction I make become a stored preference or pitfall, so the next ticket starts smarter.
- **Evaluation:** keep enough local evidence (iterations, escalations, requests, outcomes) to tune tiers and prompts later.

### 2.2 Non-Users (v1)

- Teams sharing one pipeline instance, or anyone needing a multi-ticket board.
- Trivial fixes (typos, config tweaks): they stay outside the pipeline.
- Users of harnesses other than VS Code Copilot.

### 2.3 Key User Journey

- **UJ-1. Bfranchi ships PROJ-123 between meetings.**
  Bfranchi moves PROJ-123 to In Execution in Jira. Within two minutes the poller picks it up, creates its Intent Record, and a desktop notification says "PROJ-123 ready, run start-ticket". They run `start-ticket` in Copilot. A few minutes later an elicitation prompt shows the Spec: six Given/When/Then ACs, one tagged `[assumption]`. They fix the Assumption and approve. The Plan follows: two Goals, eight Checklist Items, eleven Scenarios. They approve. Goals are implemented test-first; each finished agent run commits. Checks and the Trace Matrix are clean; three Reviewers and a Synthesizer report every AC met. The push prompt shows a Walkthrough: what changed, what to look at, how to test. They approve the push. CI fails on one integration test; a Patch Plan arrives that reuses the approved Spec. They approve it, the fix lands, they approve the second push, CI goes green, and the card moves to In Tests with a PR link.
  **Edge case:** the implementer reports Status Code `2` on Goal G2 after two different approaches. Bfranchi sees the Handoff summary in an elicitation prompt, approves Escalation to the `high` Tier, and the escalation agent resolves it in one pass.

## 3. Glossary

- **Ticket** — A Jira issue the poller picks up. One Ticket has exactly one Intent Record.
- **Intent Record** — The folder `tickets/<KEY>/` holding everything about one Ticket: Ticket snapshot, Spec, Plan, Patch Plans, State, Memlog, Handoffs, Gate Records, Failure Payloads, Run Metrics.
- **Stage** — One node of the Stage Graph (e.g. `spec`, `plan`, `implement`, `push`). Stages run in the order the Stage Graph defines.
- **Stage Graph** — The declarative definition of Stages, their order, their Gates and their loop-back edges, read by the State Tool.
- **State** — The machine-readable status of one Intent Record: current Stage, Wait Reason, counters, timestamps.
- **State Tool** — The deterministic MCP tool that reads the Stage Graph and State and tells the Conductor what to do next. All ordering logic lives here.
- **Conductor** — The cheap agent running in the main Copilot chat. It asks the State Tool for the next action, performs it, and reports back. It holds no pipeline logic.
- **Gate** — A Stage boundary that cannot be passed without a Gate Record. Gate kinds: `spec`, `plan`, `escalation`, `push`.
- **Gate Record** — The stored result of one human decision at a Gate: decision (`approve | edit | reject`), elicitation id, timestamp, hash of the approved artifact.
- **Wait Reason** — Why a Ticket is paused waiting for the human: `gate_spec | gate_plan | escalation | push`. Equivalent to AI-DLC's park.
- **Spec** — The condensed, single-source requirements document for a Ticket (`requirements.md`), built from the Jira issue, its comments and linked content. Ground truth for the Ticket.
- **Acceptance Criterion (AC)** — A numbered (`AC-n`) Given/When/Then statement in the Spec.
- **Assumption** — An AC or Spec statement inferred rather than sourced from the Ticket; tagged `[assumption]` and resolved at the `spec` Gate.
- **Plan** — The document (`plan.md`) that breaks the Spec into Goals, Checklist Items and Scenarios.
- **Goal** — First-order slice of the final deliverable. Maps to one or more ACs. Has `depends_on`, `parallel_group` and an expected file set.
- **Checklist Item** — A small implementation step under a Goal; the logical basis for one or more Scenarios.
- **Scenario** — A Given/When/Then test description under a Checklist Item, tagged `new | change | existing`.
- **Wave** — A set of Goals the scheduler allows to run together, computed from `depends_on`, `parallel_group` and file overlap.
- **Patch Plan** — A Plan revision created after a CI failure. Reuses the approved Spec unchanged.
- **Correct-Course Proposal** — A proposal to change the Spec or Plan because CI showed them to be wrong. Applies only after human approval.
- **Persona** — A role prompt (implementer, refactorer, intake, planner, reviewer, synthesizer, committer, escalation) composed with the shared senior-engineer base prompt.
- **Tier** — A model class (`cheap | medium | high`) mapped to a concrete Copilot model in config.
- **Status Code** — The value every implementer and refactorer run must end with: `0` done, `1` not done (retry in fresh context), `2` stuck (escalation requested).
- **Escalation** — Re-running a Persona's task on the `high` Tier via the escalation agent, after an approved `escalation` Gate.
- **Handoff** — The schema-validated file describing an Escalation's scope, progress, attempts and ask; the only input the escalation agent reads besides the paths it lists.
- **Check** — A deterministic lint, type or test run executed by a tool, never by a model.
- **Failure Payload** — The trimmed, shared-schema output of a failed Check, test run or CI job.
- **Trace Matrix** — The deterministic AC → Goal → Checklist Item → Scenario → test → result table.
- **Reviewer** — A cheap-Tier agent that reviews one bundle of the change against the Spec and Plan in a fresh context.
- **Synthesizer** — The medium-Tier agent that merges Reviewer outputs (or parallel Goal outputs) into one verdict and resolves conflicts.
- **Walkthrough** — The push-Gate summary: purpose of the change, what to look at closely, how to test.
- **Memlog** — The append-only decision log of an Intent Record; agents read it instead of transcripts.
- **Claim** — A Memlog entry a parallel subagent posts before it acts: its Goal, the files it will create or modify, and its intent. Open while the subagent runs; other subagents must not edit claimed files.
- **Preferences Doc** — Repo-level file of the user's recorded preferences, derived from Gate edits.
- **Pitfalls Doc** — Repo-level file of known agent mistakes, derived from Gate edits and failed attempts.
- **Project Context** — The AGENTS.md block with stable repo knowledge every Persona starts from.
- **Run Metrics** — Local per-Ticket record of iterations, escalations, requests, loops and outcome.

## 4. Features

### 4.0 Pipeline Overview

Every Ticket goes through the same steps in this order. Each step is a Stage in the Stage Graph (FR-4); the State Tool enforces the order and the Conductor only executes it. The features below (4.1–4.13) specify each step.

| # | Step (Stage) | What happens | Done by | Human approval | Specified in |
|---|---|---|---|---|---|
| 0 | Trigger | Bfranchi moves the Ticket to In Execution in Jira | Human | | §4.1 |
| 1 | Intake | Poller finds the Ticket, creates the Intent Record, sends a notification; Bfranchi runs `start-ticket` | Tool | | FR-1–3 |
| 2 | Spec (`spec`) | Ticket, comments and links condensed into a Spec with Given/When/Then ACs; Assumptions tagged | intake (cheap) | **Approve Spec** | FR-11–12 |
| 3 | Plan (`plan`) | Spec broken into Goals → Checklist Items → Scenarios; Waves computed | planner (medium) + tool | **Approve Plan** | FR-13–14 |
| 4 | Implement (`implement`) | Per Goal, in Wave order: Red → test triage → Green → Refactor; each run ends with a Status Code and commits on `0` | implementer, refactorer (cheap) + tools | Only if Status Code `2`: **Approve Escalation** | FR-15–18, FR-24–25 |
| 5 | Checks (`checks`) | Lint, types and full test suite for the Goal; failures only | Tool | | FR-19–20 |
| 6 | Trace (`trace`) | AC → Goal → Item → Scenario → test → result; any gap blocks | Tool | | FR-21 |
| 7 | Validate (`validate`) | Parallel Reviewers per bundle, then one Synthesizer verdict per AC | Reviewers (cheap), Synthesizer (medium) | | FR-22–23 |
| 8 | Push (`push`) | Walkthrough written; on approval, branch pushed and PR opened | committer (cheap) + tools | **Approve Push** | FR-26 |
| 9 | CI (`ci`) | GitHub Actions watched until a terminal state | Tool | | FR-27 |
| 10a | Patch (`patch_plan`) | On CI failure: Patch Plan against the unchanged Spec (or a Correct-Course Proposal) | planner (medium) | **Approve Patch Plan** (same as step 3) | FR-28–29 |
| 10b | Done (`done`) | On CI success: Ticket moved to In Tests, PR link commented, Run Metrics saved | Tool | | FR-30, FR-35 |

**Loop-backs:**
- Step 5 failure, step 6 gap or step 7 `partial`/`missing` → back to step 4 for the affected Goal, then forward again.
- Step 4 Status Code `1` → same task again in a fresh context.
- Step 10a approved → steps 4–8 again, ending at the push approval.
- Correct-Course Proposal approved → back to step 2 or 3 with the revised artifact.

```
In Execution ─► 1 Intake ─► 2 Spec [H] ─► 3 Plan [H] ─► 4 Implement ─► 5 Checks ─► 6 Trace ─► 7 Validate ─► 8 Push [H] ─► 9 CI
                                 ▲            ▲            ▲   │ status 2 → Escalation [H]      │          │          │                  │
                                 │            │            └───┴──────── fix ◄────────────────┴──────────┴──────────┘                  │
                                 │            └──────── 10a Patch Plan [H] ◄──────────────── fail ◄────────────────────────────────────┤
                                 └──────── Correct-Course [H] (from 10a)                                                pass ─► 10b In Tests
```

`[H]` = Bfranchi approves through an elicitation prompt (FR-8). Everything without `[H]` runs without stopping.

### 4.1 Ticket Intake

**Description:** The user signals intent in Jira itself: moving a Ticket to In Execution is the trigger, so no custom label or Jira admin setup is needed. A deterministic poller finds Tickets assigned to the user in In Execution that have no Intent Record yet, creates their Intent Records and notifies the user. The user then starts the pipeline in Copilot with `start-ticket`. No model is called. Realizes UJ-1.

#### FR-1: Poll Jira for eligible Tickets

The system polls Jira with a configurable JQL query on a configurable interval and selects Tickets with no existing Intent Record.

**Consequences (testable):**
- Default JQL is `assignee = currentUser() AND status = "In Execution"`; default interval is 120 s; both are read from config.
- The query uses only standard fields (assignee, status); it needs no custom label, field or Jira admin rights.
- A Ticket whose key already has a `tickets/<KEY>/` folder is never selected again.
- Selecting a Ticket only prepares it; the pipeline runs only when the user runs `start-ticket`, so Tickets moved to In Execution for manual work cost nothing. `[ASSUMPTION: an unused Intent Record is acceptable; a "skip" command may remove it]`
- Jira credentials are read only from environment variables; startup fails with a named error if they are missing.
- A Jira API failure is logged and retried on the next interval; it never crashes the poller.
- Polling sits behind a `TicketSource` interface, so a webhook source can replace it without changes elsewhere.

#### FR-2: Create the Intent Record

On selecting a Ticket, the system writes the Ticket snapshot, an initial State and an empty Memlog.

**Consequences (testable):**
- `tickets/<KEY>/ticket.json` contains summary, description, comments, links and attachments metadata.
- `state.yml` starts at Stage `spec` with all counters at 0.
- The Memlog's first entry records Ticket selection with a timestamp.

#### FR-3: Notify

The system sends a desktop notification naming the Ticket and the next command. It does not change the Ticket's Jira status; the user already moved it to In Execution.

**Consequences (testable):**
- The notification text is "<KEY> ready, run start-ticket".
- No Jira transition is made at intake; the only transition the pipeline makes is to In Tests (FR-30).

### 4.2 Pipeline Engine

**Description:** A Stage Graph defines the Stages, Gates and loop-back edges. The State Tool reads it and the State, and returns exactly one next action. The Conductor follows it. This replaces AI-DLC's hook-driven engine with tool calls the agent must make, keeping the orchestrator's context small. Realizes UJ-1.

#### FR-4: Declarative Stage Graph

The Stage Graph is a YAML file defining Stages, their order, their Gates, their owner (tool or Persona), and loop-back edges.

**Consequences (testable):**
- The MVP graph contains: `spec`, `plan`, `implement`, `checks`, `trace`, `validate`, `push`, `ci`, `patch_plan`, `done`.
- Loop-back edges exist for: Check failure → `implement`; Trace Matrix gap → `implement`; validation gap → `implement`; CI failure → `patch_plan`; approved Patch Plan → `implement`.
- The State Tool rejects a graph with an unreachable Stage or a Gate on a non-existent Stage.

#### FR-5: Single next action

The Conductor obtains the next action with `state_get` and reports completion with `state_advance`; the State Tool refuses out-of-order advances.

**Consequences (testable):**
- `state_get` returns one action: a tool to call, a Persona to run with its input bundle, or a Gate to open.
- `state_advance` for a Stage that is not current returns an error and changes nothing.
- `state_advance` past a Gate without a matching Gate Record returns an error.
- Every advance appends one Memlog entry.
- The State Tool keeps an HMAC of `state.yml`; a hand edit is detected on the next call and refused with an error naming the file.

#### FR-6: Wait and resume

When human input is needed, the State records a Wait Reason; a new Copilot session resumes from the recorded State.

**Consequences (testable):**
- Wait Reason is one of `gate_spec | gate_plan | escalation | push`.
- Running `start-ticket <KEY>` on a waiting Ticket re-opens the pending Gate rather than restarting the Stage.
- Running `start-ticket <KEY>` mid-Stage restarts that Stage in a fresh context with the same inputs.

#### FR-7: Effort counters

The State tracks effort counters; tools echo them in their outputs as evidence.

**Consequences (testable):**
- Counters: `scenario.iteration`, `goal.validation_rounds`, `ticket.patch_loops`, `goal.status1_retries`, `ticket.escalations`.
- `run_tests` output includes the current iteration and how many consecutive runs had the same failure signature.
- No counter value ever blocks progress (no caps).

### 4.3 Human Gates

**Description:** Four Gates stop the pipeline for a human decision. Each is opened through an MCP elicitation prompt. Because hooks are not allowed, the gate tools themselves enforce human presence: only an elicitation response can produce a Gate Record. Realizes UJ-1.

#### FR-8: Elicitation-only approval

A Gate Record can only be created from a human's answer to an MCP elicitation prompt raised by `gate_request`.

**Consequences (testable):**
- No tool accepts an approval decision as an argument from the agent.
- A Gate Record stores decision, elicitation id, timestamp and the SHA-256 of the artifact shown.
- If the elicitation is cancelled or times out, the Ticket stays waiting with its Wait Reason; nothing advances.
- If the client does not support elicitation, `gate_request` uses the fallback channel in FR-42.

#### FR-9: Gate content

Each Gate shows the artifact and the evidence needed to decide.

**Consequences (testable):**
- `spec` Gate: the Spec, with every `[assumption]` listed first.
- `plan` Gate: the Plan, plus computed Waves and any scheduler warnings.
- `escalation` Gate: the Handoff summary (reason, attempts, ask, target Tier).
- `push` Gate: the Walkthrough, Trace Matrix summary, synthesized verdict and commit list.
- Options are `approve`, `edit` (free text returned to the authoring Persona) and `reject` (stops the Ticket with Wait Reason kept).

#### FR-10: Approved artifacts are frozen

After approval, the Spec and Plan are read-only to Personas; changing them requires a new Gate.

**Consequences (testable):**
- Before any Stage runs, the State Tool compares the current hash of the Spec and Plan with their Gate Records; a mismatch blocks the Stage and re-opens the matching Gate.
- During a patch loop the Spec hash must equal the originally approved hash.

#### FR-40: Per-Stage tool sets

Each Stage runs with a Copilot agent whose tool set contains only the tools that Stage needs, so actions a Stage must not take are unavailable rather than merely forbidden. *(IDs FR-40–42 were added after the first draft; numbering stays stable.)*

**Consequences (testable):**
- The generator (FR-38) writes each Persona's agent file with an explicit tool allowlist taken from the Stage Graph.
- Before the `plan` Gate is approved, no running agent has file-edit or terminal tools; intake and planner write only through `doc_scaffold`.
- No agent has raw `git push` or Jira-write tools; commits, pushes and transitions go only through the MCP tools in FR-17, FR-26 and FR-30.
- The Conductor's tool set is limited to `state_get`, `state_advance`, `gate_request` and subagent launch.
- `[verify: OQ-8]` Copilot enforces per-agent tool allowlists for subagents.

#### FR-41: Detect pre-approval changes

At each transition and before each commit, the State Tool checks that no source change predates the approval it depends on.

**Consequences (testable):**
- When the `plan` Gate is approved, the State Tool records a snapshot (git tree hash of the working tree).
- At `state_advance` from `implement` and at `commit_prepare`, any working-tree difference against the approval snapshot that the State Tool cannot attribute to an implement Stage run fails with an error listing the files.
- The same check runs for an approved Patch Plan, against a snapshot taken at its approval.

#### FR-42: Fallback approval channel

If MCP elicitation is unavailable, `gate_request` falls back to an approval tool that Copilot always asks the human to confirm.

**Consequences (testable):**
- The fallback tool `gate_confirm` is declared so that Copilot always shows its confirmation dialog and never auto-approves it. `[verify: OQ-1]`
- A Gate Record created this way stores `channel: tool_confirmation` instead of an elicitation id.
- The Memlog records which channel each Gate used.
- If neither channel is available, `gate_request` fails with an explicit error and the Ticket stays waiting.

### 4.4 Spec

**Description:** The intake Persona (cheap) condenses the Ticket, its comments and linked content into one Spec, in the manner of `bmad-spec`. ACs are Given/When/Then. Anything inferred is tagged so the human resolves it at the `spec` Gate. Realizes UJ-1.

#### FR-11: Generate the Spec

The intake Persona produces `requirements.md` from `ticket.json` via the `doc_scaffold` template.

**Consequences (testable):**
- Every AC has an `AC-n` id and Given/When/Then form; the scaffold tool rejects an AC without all three clauses.
- Every AC carries a source tag: the Jira field or comment it came from, or `[assumption]`.
- The Spec contains an "Out of scope" list, which may be empty.

#### FR-12: Resolve Assumptions at the Gate

The `spec` Gate cannot be approved while any `[assumption]` tag remains unaccepted.

**Consequences (testable):**
- Approval requires each Assumption to be accepted, edited into a sourced AC, or removed.
- Accepted Assumptions stay tagged `[assumption: accepted]` for traceability.

### 4.5 Plan

**Description:** The planner Persona (medium) breaks the approved Spec into Goals, Checklist Items and Scenarios. Good Scenario design is where vacuous tests and scope creep are prevented. A deterministic scheduler computes Waves. Realizes UJ-1.

#### FR-13: Generate the Plan

The planner produces `plan.md` with Goals → Checklist Items → Scenarios.

**Consequences (testable):**
- Each Goal lists `acs`, `depends_on`, `parallel_group` and expected `files`.
- Each Checklist Item has at least one Scenario; each Scenario has a tag `new | change | existing` and Given/When/Then text.
- Every AC is covered by at least one Goal; the scaffold tool rejects a Plan with an uncovered AC.
- Each Scenario states the observable assertion it expects (value, state change or error), not only the action. `[ASSUMPTION: this is how "planner prevents vacuous tests" is made checkable]`

#### FR-14: Compute Waves

`plan_schedule` computes Waves from `depends_on`, `parallel_group` and file overlap, without a model.

**Consequences (testable):**
- A dependency cycle is reported to the planner with the Goals involved.
- Goals in the same `parallel_group` with overlapping `files` are moved into sequential Waves, and a warning is shown at the `plan` Gate.

### 4.6 TDD Implementation

**Description:** For each Goal, the implementer (cheap) runs Red → Green, then the refactorer (cheap, fresh context) refactors. Every run ends with a Status Code and, when done, a commit. Test triage flags anomalies deterministically. Realizes UJ-1.

#### FR-15: Red, Green, Refactor per Goal

Each Goal is implemented test-first in fresh-context subagent runs.

**Consequences (testable):**
- Red: tests are written for the Goal's Scenarios before production code changes.
- The refactorer receives only the Plan section, changed files and green results.
- Goals run in Wave order; within a Wave they run sequentially unless parallel mode is on (§4.11).

#### FR-16: Mandatory Status Code

Every implementer and refactorer run ends with a Status Code that the State Tool parses deterministically.

**Consequences (testable):**
- A run without a parseable `0 | 1 | 2` is treated as `1`.
- `0` triggers the Goal's Checks (FR-19).
- `1` relaunches the same task in a fresh context and increments `goal.status1_retries`.
- `2` creates a Handoff and opens the `escalation` Gate (FR-25).

#### FR-17: Granular commits

Each implementer or refactorer run that ends with Status Code `0` commits its own changes as its last action.

**Consequences (testable):**
- Commits go only to the Ticket's feature branch; the commit tool refuses protected branches.
- Commit messages reference the Ticket key and Goal id.
- No push happens outside the `push` Gate.

#### FR-18: Test triage

`test_triage` classifies new-test results by Scenario tag and reports only anomalies.

**Consequences (testable):**
- Reported anomalies: a `new`/`change` test that passes at Red; an `existing` test that fails; a failure caused by import, compile, setup or timeout rather than an assertion.
- Classification comes from the test runner's JSON output, with no model.
- No anomalies → no output.

### 4.7 Checks

**Description:** After a Goal reaches Status Code `0`, lint, type checks and the full test suite run automatically. Clean results cost nothing; failures return a trimmed payload. Realizes UJ-1.

#### FR-19: Per-Goal Checks

`run_checks` runs automatically after each Goal's Status Code `0`.

**Consequences (testable):**
- Checks do not run per file write.
- A clean run returns a one-line status and triggers no model call.
- A failed run returns Failure Payloads and loops back to the implementer for that Goal.

#### FR-20: Shared Failure Payload schema

Checks, test runs and CI failures share one Failure Payload schema.

**Consequences (testable):**
- Each failure has: source (`lint | types | test | ci`), name, `file:line`, message (≤ 15 lines).
- CI payloads may add job and step fields; all other fields keep the same names.

### 4.8 Validation

**Description:** After all Goals pass Checks, a deterministic Trace Matrix proves coverage, then several cheap Reviewers check behaviour against the Spec in parallel and a medium Synthesizer merges their findings. Realizes UJ-1.

#### FR-21: Blocking Trace Matrix

`trace_matrix` builds AC → Goal → Checklist Item → Scenario → test → result and blocks progress on any gap.

**Consequences (testable):**
- Gaps are: an AC with no Scenario, a Scenario with no test, or a test that is not passing.
- Any gap routes the affected Goal back to implementation, then Checks and validation re-run. `[ASSUMPTION: "re-iterate steps 5 and 6" means go back through implementation for the gap]`
- No gap → the validation Stage starts; no model is called to build the matrix.

#### FR-22: Parallel Reviewers

The system splits the change into review bundles sized to the cheap Tier's context window and runs one Reviewer per bundle in parallel.

**Consequences (testable):**
- Bundle size limit comes from config per Tier; a bundle never exceeds it.
- Bundles are split by Goal first, then by file.
- Each bundle holds: the relevant Spec ACs, the Plan section, the diff slice, the Trace Matrix rows and the Memlog.
- Each Reviewer returns `{ac_id: met | partial | missing, evidence, gaps}` for its ACs.

#### FR-23: Synthesized verdict

A medium-Tier Synthesizer merges Reviewer outputs into one verdict per AC and per Goal.

**Consequences (testable):**
- Contradicting Reviewer verdicts on the same AC are resolved with a stated reason.
- Any `partial` or `missing` AC routes the affected Goal back to implementation with the gap list and increments `goal.validation_rounds`.
- The verdict cannot rest on "tests pass" alone; each `met` cites evidence from the diff or a test.

### 4.9 Escalation

**Description:** When a cheap Persona reports it is stuck (Status Code `2`), the system builds a structured Handoff and asks the human whether to escalate. If approved, the escalation agent works the task in the original role on the `high` Tier. Realizes UJ-1.

#### FR-24: Structured Handoff

`handoff_create` writes a schema-validated Handoff to `tickets/<KEY>/handoffs/H-n.yml`.

**Consequences (testable):**
- Required fields: from Persona and Tier, role prompt path, reason (`stuck | cross_module | spec_conflict | quality_review`), scope (Goal, Scenarios, files), progress counters, attempts (one line each), ask (one sentence), constraints, expected return type.
- An invalid Handoff is rejected with the failing field named.

#### FR-25: Human-approved Escalation

A Status Code `2` opens the `escalation` Gate; only on approval does the escalation agent run.

**Consequences (testable):**
- On `reject`, the human can provide guidance that is passed to a fresh cheap run, or stop the Ticket.
- The escalation agent reads only the Handoff and the paths it lists.
- It returns `{status: resolved | partial | cannot, summary, files_changed, follow_ups}`; the caller sees only that.
- Every Escalation is logged in the Memlog with its reason.

### 4.10 Push, CI and Patch Loop

**Description:** The `push` Gate shows a Walkthrough; on approval the branch is pushed and a PR opened. CI is watched deterministically. On failure, a Patch Plan is drafted against the unchanged Spec and must be approved before any code is generated. On success, the Ticket moves to In Tests. Realizes UJ-1.

#### FR-26: Walkthrough and push

The committer Persona (small) writes the Walkthrough; on `push` Gate approval the system pushes the feature branch and opens a PR.

**Consequences (testable):**
- The Walkthrough has three parts: purpose, what to look at closely, how to test.
- Push targets only the Ticket's feature branch.
- A PR is created (or updated) with the Walkthrough as its body. `[ASSUMPTION: the pipeline opens the PR; v5 only says "Jira comment with PR link"]`

#### FR-27: CI watch

`ci_watch` polls GitHub Actions for the pushed commit until it reaches a terminal state.

**Consequences (testable):**
- Terminal states: success, failure, cancelled, timed out.
- On failure, `ci_failure` produces Failure Payloads (FR-20) in `ci_failure.json`.
- No model is called while waiting.

#### FR-28: Patch Plan with approval

On CI failure, the planner drafts a Patch Plan that reuses the approved Spec, and the `plan` Gate must approve it before implementation resumes.

**Consequences (testable):**
- The Patch Plan is written to `patch-<n>.md`; `ticket.patch_loops` increments.
- The Spec is not modified (FR-10 hash check).
- After approval the loop runs implement → checks → trace → validate → push Gate.
- Nothing is generated between CI failure and Patch Plan approval except the Patch Plan itself.

#### FR-29: Correct-Course Proposal

If the planner judges that the Spec or Plan itself is wrong, it writes a Correct-Course Proposal instead of a Patch Plan.

**Consequences (testable):**
- The proposal names the affected ACs or Goals, the evidence from CI, and the proposed change.
- Approving it re-opens the `spec` or `plan` Gate with the revised artifact; rejecting it returns to Patch Plan drafting with the human's note.

#### FR-30: Done

On CI success, the system transitions the Ticket to In Tests and comments the PR link on the Jira issue.

**Consequences (testable):**
- The Jira comment contains the PR URL and nothing else required. `[ASSUMPTION: no summary in the Jira comment; retrospective stays local per Q30]`
- State moves to `done`; Run Metrics are finalized (FR-35).

### 4.11 Parallel Goal Execution (behind a flag)

**Description:** When enabled, Goals in the same Wave run as parallel subagents. They share the Memlog. Launches are gated by the log, not by a timer: each subagent's first act is to post a Claim (the files it will work on and its intent), and the launcher watches the Memlog and starts the next subagent only once that Claim appears. Every later subagent reads the open Claims first and stays out of the claimed files. Each subagent runs in its own terminal, and a Synthesizer reconciles conflicts afterwards. Off by default until the sequential loop is stable.

#### FR-31: Parallel mode switch

A config flag `parallel: true | false` (default `false`) controls whether Waves run in parallel.

**Consequences (testable):**
- With `false`, all Goals run one at a time in Wave order.
- The flag can be overridden per Ticket in its State.

#### FR-32: Claim-gated launches on a shared log

In parallel mode, the launcher starts subagents in a Wave one at a time and waits for each one's Claim in the shared Memlog before starting the next. Subagents append to the shared Memlog and run commands in separate terminals.

**Consequences (testable):**
- A subagent's first action, before any file edit or command, is `claim_post`, which appends a Claim entry to the Memlog: Goal id, the files it will create or modify, and a one-sentence intent.
- The launcher (deterministic, no model) watches the Memlog and launches the next subagent only after the previous subagent's Claim is written.
- Each subagent receives the open Claims of its Wave in its input bundle and must not edit a file claimed by another open Claim.
- A subagent that needs a file outside its Claim posts a Claim update first; if that file is claimed by another open Claim, the update is refused and the subagent ends with Status Code `2` (`reason: cross_module`).
- `commit_prepare` refuses changes to files outside the subagent's own Claim, listing them.
- A Claim is closed when its subagent ends (any Status Code); closed Claims stay in the Memlog for the Synthesizer.
- If no Claim appears within a configurable timeout, the launcher marks that subagent failed (treated as Status Code `1`) and launches the next one. `[ASSUMPTION: default timeout 120 s]`
- Each subagent's terminal and test run is isolated; tests are scoped to the Goal.
- Memlog appends are atomic; concurrent appends never interleave within an entry.

#### FR-33: Wave synthesis

After a parallel Wave, a Synthesizer checks the combined change for conflicts and coherence before Checks run.

**Consequences (testable):**
- File conflicts or contradicting changes are reported with the Goals involved and routed back to implementation.
- A clean synthesis lets the Wave proceed to Checks.

### 4.12 Memory and Learning

**Description:** Each Ticket keeps a Memlog. Gate edits and failed attempts feed two repo-level documents (Preferences, Pitfalls) that every Persona reads, alongside the Project Context. Run Metrics stay local for later evaluation.

#### FR-34: Ticket Memlog

Every Stage, Gate decision, Escalation and loop appends one line to the Ticket's Memlog.

**Consequences (testable):**
- Entries are append-only, timestamped and typed (`decision | change | event | assumption | escalation`).
- Reviewers and the escalation agent receive the Memlog, never chat transcripts.

#### FR-35: Run Metrics

On `done` (or a stopped Ticket), the system writes Run Metrics locally.

**Consequences (testable):**
- Fields: premium requests by Persona and Tier, counters from FR-7, Gate decisions (approve/edit/reject), patch loops, Escalations by reason, wall-clock time from selection to `done`.
- Metrics are never posted to Jira.

#### FR-36: Preferences and Pitfalls

When a human `edit` at a Gate changes an artifact, the system proposes a Preferences or Pitfalls entry for the human to accept.

**Consequences (testable):**
- The proposal appears in the same elicitation flow after the edit; nothing is written without acceptance.
- Accepted entries are appended to the Preferences Doc or Pitfalls Doc with the Ticket key as source.
- Both docs are included in every Persona's input bundle.

#### FR-37: Project Context

Every Persona starts from the repo's Project Context (AGENTS.md block, `bmad-project-context` style) and one shared knowledge bundle.

**Consequences (testable):**
- The Project Context is created once per repo and refreshed on request, not per Ticket.
- There are no per-Persona knowledge folders in the MVP.

### 4.13 Personas and Model Tiers

**Description:** All Personas share a senior-engineer base prompt and differ only in their role prompt. A generator composes them into Copilot agent files. Tiers map to concrete Copilot models through a config command with project and local layers.

#### FR-38: Composed Personas

A generator composes `_senior-base.md` with each role prompt into the Copilot agent files.

**Consequences (testable):**
- Running the generator twice with no input change produces identical files.
- Editing the base prompt changes every generated agent on the next run.

#### FR-39: Tier configuration

A CLI command sets a Persona's Tier, or a Tier's model, at project or local level; local overrides project.

**Consequences (testable):**
- Default Tiers: intake `cheap`, planner `medium`, implementer `cheap`, refactorer `cheap`, Reviewer `cheap`, Synthesizer `medium`, committer `cheap`, Conductor `cheap`, escalation `high`.
- An unknown Persona or model id is rejected with the valid values listed.

## 5. Cross-Cutting NFRs

- **NFR-1 Token economy:** deterministic Stages (poll, transition, schedule, checks, triage, Trace Matrix, CI watch, metrics) make zero model calls. Model-facing tool outputs are trimmed (failures and anomalies only; ≤ 15 lines per failure).
- **NFR-2 No hooks:** no feature depends on harness hooks. Ordering, Gates, freezes and human presence are enforced inside MCP tools.
- **NFR-3 Host:** VS Code Copilot agent mode only, with Copilot-provided models only.
- **NFR-4 Determinism:** the same State and inputs give the same `state_get` action. Tool outputs are machine-parseable.
- **NFR-5 Resumability:** a Copilot session can end at any point; `start-ticket <KEY>` resumes from State (FR-6).
- **NFR-6 Security:** secrets only from environment variables. Push only to feature branches. Jira token scoped to read, transition and comment.
- **NFR-7 Formats:** YAML for config, schemas and frontmatter; Markdown for prompts and documents; TypeScript for tool logic. No other formats.
- **NFR-8 Fresh context:** every Persona run gets an explicit input bundle and no prior chat history.
- **NFR-9 Error surfacing:** every external call (Jira, git, GitHub, test runners) returns a typed error to the caller; nothing fails silently.
- **NFR-10 Context budget:** ambient instructions (`.github/copilot-instructions.md` plus the Project Context block loaded every session) stay at or below 150 tokens, naming only the MCP server and its first call. Framework text per step (Persona prompt, rules, tool guidance returned by `state_get`) stays at or below 3K tokens, excluding the work content (Ticket, Spec, Plan slice, code, test output). `state_get` returns paths and a prompt id, plus only the rules that step needs. Budgets are checked by a deterministic token estimate in the generator and the State Tool; an over-budget prompt fails generation. For comparison, the AI-DLC token review measured about 12K ambient and 15–45K per stage.

## 7. Non-Goals (Explicit)

- Not a general AI-DLC or BMAD replacement: no ideation, inception design stages, architecture docs or operations.
- Not a team tool: no shared board, no multi-user approvals.
- Not autonomous: no Stage that produces code runs without an approved Spec and Plan (or Patch Plan).
- Not harness-portable: no Claude Code, Cursor, Codex or Kiro support.
- No auto-merge and no deployment.

## 8. MVP Scope

### 8.1 In Scope

- Jira poller, Intent Record, transitions, notification.
- Stage Graph, State Tool, Conductor, resume.
- Four elicitation Gates (with tool-confirmation fallback) and frozen artifacts.
- Per-Stage tool sets, pre-approval change detection, State integrity check, context budgets.
- Spec, Plan, Waves, sequential TDD, triage, per-Goal Checks, granular commits.
- Trace Matrix, parallel Reviewers + Synthesizer.
- Status Codes, human-approved Escalation with Handoff.
- Walkthrough, push, PR, CI watch, Patch Plan loop, Correct-Course Proposal, In Tests.
- Ticket Memlog, Run Metrics, Preferences and Pitfalls docs, Project Context.
- Persona generator and Tier config.
- Parallel Goal execution behind a flag (shipped last).

### 8.2 Out of Scope for MVP

- Multi-ticket sprint-status board — v2.
- Composer-style ticket triage and right-sized scopes (bugfix/express paths) — v2.
- Layered prompt customization (team/personal overrides) — later; high value.
- Obsidian integration and RAG/graphRAG search — later.
- Epic → story splitting; practices discovery; team testing-posture customization.
- Per-scope test floors; E2E/API test generation.
- Review-only second-opinion agent before Escalation; party-mode debates.
- Jira webhooks (the `TicketSource` interface allows them later).
- Retrospectives posted to Jira.
- Trivial fixes (handled outside the pipeline).

## 9. Success Metrics

**Primary**
- **SM-1:** Tickets reaching In Tests with no hand-written production code — target ≥ 70% of eligible Tickets over the first 20. Validates FR-11–30.
- **SM-2:** Premium requests per Ticket — target below the manual Copilot baseline measured on 5 comparable Tickets. Validates NFR-1, FR-19, FR-21.

**Secondary**
- **SM-3:** Model calls made by deterministic Stages — target 0. Validates NFR-1.
- **SM-4:** Gate `edit` rate on Spec and Plan — tracked per Ticket; a falling trend after Preferences/Pitfalls accumulate shows learning works. Validates FR-36.
- **SM-5:** Escalations per Ticket by reason, and patch loops before green. Validates FR-24–28.

**Counter-metrics (do not optimize)**
- **SM-C1:** Gate time-to-approve — don't drive it down by rubber-stamping; the Gates exist to catch errors. Counterbalances SM-1.
- **SM-C2:** Escalation count — don't suppress Escalations to save requests if it raises patch loops. Counterbalances SM-2.
- **SM-C3:** Test count per Goal — more tests is not better; Scenarios should map to Checklist Items. Counterbalances SM-1.

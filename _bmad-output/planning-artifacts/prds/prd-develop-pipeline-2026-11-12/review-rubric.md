# PRD Quality Review — Agentflow MVP (prd-develop-pipeline-2026-11-12)

## Overall verdict
This is a well-built PRD for a single-operator tool. It has a sharp thesis ("token economy through determinism"), a fixed glossary that is used consistently, a numbered pipeline table, and testable consequences on almost every FR. Most of it can be handed to story creation as it stands. The risk sits in the State Tool, the part the PRD itself says holds "all ordering logic". Several state-machine behaviours are undefined or contradictory: what reject does at each Gate, how a Ticket stops, how the TDD runs are split, which loop-back edges exist, and whether FR-41's snapshot can detect anything. The "no caps" decision is also left without a stated trade-off, even though it can burn premium requests with no human stop. Fix these before generating epics. The rest needs only light cleanup.

## Decision-readiness — adequate
Decisions are stated as decisions, not as "considerations". Examples: "No counter value ever blocks progress (no caps)" (FR-7), "Not autonomous" (§7), the trigger is a plain status move with "no custom label, field or Jira admin rights" (FR-1), and "Where this PRD and v5 disagree, this PRD wins" (§0). The open questions are real, not rhetorical. OQ-1, OQ-7 and OQ-8 are genuine Copilot-capability unknowns, and OQ-1 is flagged "prove in week 1". Most trade-off reasoning lives in addendum §H rather than the PRD, which is acceptable for a personal tool.

The gaps: the riskiest decision ("no caps") is stated without what it gives up, and the PRD has no plan B if its foundational unknown (OQ-1) comes back negative.

### Findings
- **high** "No caps" has no stated trade-off and no human stop inside the inner loops (FR-7, FR-16, §4.0 Loop-backs). Status Code `1` relaunches "in a fresh context" without limit. "A run without a parseable `0 | 1 | 2` is treated as `1`". Checks, Trace and Validate failures loop back to step 4 with no Gate in between. Addendum §C says "the human stops the patch loop at the Patch Plan Gate", but no Gate sits on the 4→7 loops. A cheap model that keeps emitting malformed output would burn premium requests with nobody watching. That works directly against the Vision's "defining constraint". *Fix:* keep "no caps" if intended, but state the trade-off and add a deterministic non-blocking stop: for example, after N identical failure signatures or N status-1 retries (config), `state_get` opens the `escalation` Gate automatically. The alternative is to state explicitly that the user accepts unbounded spend and stops it manually.
- **medium** No fallback if OQ-1 fails both ways (§10 OQ-1, FR-42). FR-42 ends with "If neither channel is available, `gate_request` fails ... and the Ticket stays waiting". That leaves a pipeline that can never pass a Gate. The PRD does not say what the MVP becomes in that case. *Fix:* name the plan B, for example an `agentflow approve <KEY>` CLI run by the human in a terminal outside the agent's tool set that writes the Gate Record. Alternatively, state that a negative OQ-1 stops the project.

## Substance over theater — strong
There is no persona theater: one user, one UJ, three Non-User lines that each exclude something real. The NFRs are product-specific with thresholds ("≤ 15 lines per failure", "at or below 150 tokens", "at or below 3K tokens", "zero model calls"). The Vision could not be swapped into another PRD, because the determinism constraint and the three fixed approval moments are specific to this tool.

### Findings
- **low** §6 Method Lineage is context rather than requirements. No FR depends on it, and a code-generation consumer gains nothing from it. *Fix:* move it to the addendum, or keep it and mark it "informative, not normative".

## Strategic coherence — adequate
The thesis is explicit and the features follow from it. Deterministic tools own polling, scheduling, checks, the Trace Matrix and CI (NFR-1). Models appear only at judgment points, and cheap Tiers are the default (FR-39). The build order in addendum §G proves the riskiest unknowns first. The Success Metrics track the thesis (SM-2, SM-3), and there are real counter-metrics (SM-C1, SM-C2). The weakness is measurability: the metric that validates the thesis has no defined data source.

### Findings
- **high** SM-2, the primary thesis metric, has no defined measurement source (SM-2, FR-35, OQ-2). FR-35 records "premium requests by Persona and Tier", but the MCP server cannot see Copilot billing, and OQ-2 says the billing model is unknown. The "manual Copilot baseline measured on 5 comparable Tickets" has no method either. As written, the metric that proves the thesis cannot be computed. *Fix:* define a proxy the tool can log itself, for example Persona runs × the per-model multiplier from config, recorded by `state_advance`. Also define how the baseline is captured.
- **medium** SM-1 lacks operational definitions (SM-1). "No hand-written production code" and "eligible Tickets" are not defined. Gate `edit`s change artifacts, not code, so nothing in the FRs records manual code edits. *Fix:* define eligible (for example, a Ticket on which `start-ticket` ran, excluding ones the user stopped). Define hand-written as any commit on the feature branch not made by `commit_prepare`, or any FR-41 detection.
- **low** SM-C3 is said to counterbalance SM-1, but test count trades off against cost (SM-2), not autonomy (§9). *Fix:* re-point it or drop the "Counterbalances" note.

## Done-ness clarity — adequate
Most FRs are exemplary: concrete defaults (FR-1 JQL and 120 s), exact strings (FR-3), schemas with named fields (FR-20, FR-24), and enumerated anomalies (FR-18). The weak spots cluster in the State Tool and the implement loop. Those are the parts code generation will build first (addendum §G Week 1 and Week 3), and they are underspecified exactly where the state machine branches.

### Findings
- **high** FR-41's snapshot cannot detect pre-approval edits, and its "attribution" is undefined (FR-41). The snapshot is taken "When the `plan` Gate is approved", so any edit made during `spec` or `plan` is already in the baseline and passes silently. That is the very case FR-41 exists for ("no source change predates the approval"). Separately, "a working-tree difference ... that the State Tool cannot attribute to an implement Stage run" names no attribution mechanism. Edits happen through Copilot's own tools, which the State Tool cannot see. *Fix:* record a baseline at `start-ticket` (HEAD plus a required clean tree), and require the tree to equal that baseline at plan approval. Define attribution as "changes committed via `commit_prepare` during a run that `state_get` launched for that Goal".
- **high** The run boundaries of the TDD loop are undefined (FR-15 to FR-17, FR-19, §4.0 step 4). Step 4 reads "Red → test triage → Green → Refactor; each run ends with a Status Code and commits on `0`". Several questions follow. Is Red a separate run? If so, its Status Code `0` would commit failing tests, and FR-16 says `0` "triggers the Goal's Checks", which would then fail. Does the implementer's `0` trigger Checks before the refactorer runs, and again after? When does `test_triage` run, and where do its anomalies route (FR-18 only says "No anomalies → no output")? *Fix:* define the sub-steps (for example `red`, `triage`, `green`, `refactor`), what each run's `0` triggers, which runs commit, and the routing for each triage anomaly.
- **high** Gate decision semantics contradict each other, and there is no stopped state (FR-9, FR-25, FR-29, FR-4, FR-6, FR-35). FR-9 defines `reject` generically as "stops the Ticket with Wait Reason kept". FR-25's reject instead passes guidance to a fresh cheap run. FR-29's reject returns to Patch Plan drafting. FR-4's graph has no `stopped` Stage, yet FR-35 writes metrics "on `done` (or a stopped Ticket)". FR-6 says `start-ticket` on a waiting Ticket re-opens the pending Gate, so a rejected Ticket cannot be told apart from a waiting one. It is also unclear whether `edit` re-runs the Persona and then re-opens the same Gate. *Fix:* add a per-Gate decision table (Gate × approve/edit/reject → next Stage and Wait Reason). Add a terminal `stopped` Stage and say how the user reaches it and whether it can be resumed.
- **medium** Correct-Course approval has no Gate kind (Glossary "Gate", "Wait Reason", FR-29). The Gate kinds are only `spec, plan, escalation, push`, and FR-29 requires human approval of the proposal itself before it "re-opens the `spec` or `plan` Gate". *Fix:* add a `correct_course` Gate kind and Wait Reason, or define the proposal as an alternative artifact shown at the `plan` Gate.
- **medium** The FR-4 loop-back list is incomplete, and escalation outcomes are unrouted (FR-4, FR-25, FR-33, §4.0 Loop-backs). FR-4's testable edge list omits Correct-Course → `spec`/`plan` and Wave-synthesis conflict → `implement` (FR-33). FR-25 returns `resolved | partial | cannot` but never says what the State Tool does with each: whether `resolved` goes to Checks and whether the escalation agent commits. *Fix:* make FR-4's edge list exhaustive and add routing consequences for each escalation return status.
- **medium** The test-to-Scenario link is unspecified (FR-21, FR-18). The Trace Matrix needs "Scenario → test → result", and triage classifies "by Scenario tag", but no FR says how a test is tied to a Scenario id. Addendum §E hints at name-prefixing ("S1.1.1 free shipping"). *Fix:* add a consequence requiring every new or changed test to carry its Scenario id in its name or an annotation, and have `trace_matrix` treat an unmapped test as a gap.
- **medium** The Assumption-resolution UX does not fit the Gate options (FR-12 vs FR-9). The Gate offers `approve | edit | reject`, but FR-12 needs each Assumption individually "accepted, edited into a sourced AC, or removed". *Fix:* specify the elicitation form, for example one accept/remove field per Assumption plus free-text edit, and the rule that turns it into `[assumption: accepted]`.
- **medium** Who writes Preferences and Pitfalls proposals is undefined (FR-36, addendum `learning_propose`). Turning a Gate edit into a reusable preference takes judgment, but no Persona or Tier is assigned, and NFR-1 does not list it as deterministic. The edit-then-propose timing is also unclear, since the revised artifact exists only after the authoring Persona reruns. *Fix:* name the Persona and Tier, or define a deterministic proposal (the diff plus the user's edit text), and say when in the flow it appears.
- **medium** Feature branch lifecycle is unspecified (FR-17, FR-26). The FRs say commits go "only to the Ticket's feature branch", but nothing says who creates it, when, its naming, its base branch, or the PR target branch. *Fix:* add an FR or consequence: the branch `<prefix>/<KEY>` is created by `start-ticket` from configured base `X`, and the PR targets `X`.
- **medium** CI non-failure terminal states are unrouted (FR-27). The terminal states include "cancelled, timed out", but only failure → `patch_plan` and success → `done` are defined. `ci_watch` also has no maximum wait or "no run found" case. *Fix:* route cancelled and timed-out (for example, Wait Reason `ci` with a re-watch option) and add a config timeout for a missing CI run.
- **low** The per-Ticket parallel override cannot be set (FR-31 vs FR-5). The flag "can be overridden per Ticket in its State", but `state.yml` is HMAC-protected and hand edits are refused, and no tool sets the flag. *Fix:* name the tool or command.
- **low** The test scope is ambiguous (FR-19, §4.0 step 5, FR-32). Step 5 reads "full test suite for the Goal", but FR-32 says "tests are scoped to the Goal". *Fix:* state whether Checks run the whole repo suite or the Goal's subset, and whether the answer differs by mode.

## Scope honesty — adequate
§7 Non-Goals and §8.2 do real work, with versioned deferrals ("v2", "later"). All six inline `[ASSUMPTION]` tags are indexed in §11. The two `[verify: OQ-n]` tags tie back to open questions. The open-item density (7 open OQs, 6 assumptions, 0 NOTE FOR PM) suits a personal build-input PRD. One omission is large enough to be silently assumed.

### Findings
- **medium** Concurrent active Tickets are neither in scope nor excluded (§2.2, §7, FR-1, FR-41). §2.2 excludes a "multi-ticket board", yet the poller prepares every In Execution Ticket. Nothing says whether two Tickets can be mid-pipeline in one working tree, which would break the FR-41 snapshots and branch handling. *Fix:* add `[NON-GOAL for MVP]`: one active Ticket per repo; `start-ticket` refuses while another Ticket is between `plan` approval and `push`.
- **low** The FR-1 assumption contradicts FR-1 itself (FR-1, §11). It says "a 'skip' command may remove" the Intent Record, but selection is defined as "Tickets with no existing Intent Record", so a removed record gets picked up again on the next poll. *Fix:* have skip write a `skipped` State instead of deleting the folder.

## Downstream usability — adequate
This dimension matters a lot here, because the PRD is chain-top for code generation. It holds up well. The glossary is complete and used in capitalized form throughout. The §4.0 table maps each step to its FRs. Each FR stands alone, with cross-references by FR id rather than "see above". The addendum supplies schemas and tool names. The issues are the state-machine gaps listed under Done-ness and a few vocabulary slips (see Mechanical notes).

## Shape fit — strong
The shape is right for a single-operator internal tool: a capability spec with one UJ carrying a named protagonist and an edge case, operational SMs, and NFRs as hard limits. UJ-1 is not overhead. It walks every Gate, a CI failure and an Escalation, which makes it a usable end-to-end acceptance script. Nothing is over-formalized.

## Mechanical notes
- **ID ordering:** FR-40 to FR-42 sit in §4.3 between FR-10 and FR-11. This is acknowledged inline ("numbering stays stable"). The IDs are unique and contiguous from 1 to 42, but generators that walk FRs in document order will see them out of sequence.
- **Tier drift:** FR-26 calls the committer "(small)". The Tier vocabulary is `cheap | medium | high`, and FR-39 says `cheap`.
- **Persona list drift:** the glossary "Persona" lists 8 roles without `conductor`, but FR-39 and addendum §F treat Conductor as a Persona with a Tier.
- **Enum naming:** the Wait Reasons `gate_spec | gate_plan | escalation | push` do not follow one pattern, unlike the Gate kinds `spec | plan | escalation | push`. Pick one pattern.
- **`start-ticket` arity:** FR-3's notification says "run start-ticket" with no key, while FR-6 and NFR-5 use `start-ticket <KEY>`. The behaviour with no key is undefined when several Tickets are prepared.
- **§2.1 JTBD:** "from Backlog to 'In Tests'" does not match the trigger, which is a manual move to In Execution (FR-1).
- **Assumptions Index roundtrip:** all 6 inline `[ASSUMPTION]` tags (FR-1, FR-13, FR-21, FR-26, FR-30, FR-32) appear in §11, and §11 has no orphans. This passes.
- **UJ protagonist:** UJ-1 names "Bfranchi" and carries context inline. This passes.
- **Required sections:** all are present for the stakes and product type.
